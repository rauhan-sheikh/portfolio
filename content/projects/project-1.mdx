# Operational Analytics Dashboard

## Overview

An internal dashboard used by support and product teams to monitor incidents, user behavior, and system health in near real time. The goal was to replace manual spreadsheet reporting with a single source of truth that anyone in the company could rely on.

## Problem

- Support teams were manually exporting CSVs from multiple tools and stitching them together.
- Product managers had no live view of feature adoption or cohort behavior.
- Engineering had metrics, but they were not accessible in a non-technical UI.

The result was delayed decision making and a lot of duplicated work. We needed a single web application that could aggregate data sources, expose opinionated dashboards, and still be maintainable by a small team.

## Architecture

The system is a **Next.js** application with a **Node.js** backend layer and a **PostgreSQL** database.

- **API Layer**: Route handlers expose REST endpoints for incidents, usage events, and feature flags.
- **Data Layer**: PostgreSQL accessed via **Prisma**, with read-optimized indexes for the most common queries (time-bounded aggregations).
- **Ingestion**: Batched ingestion jobs (Node scripts) periodically pull data from external tools and normalize them into a unified schema.
- **Frontend**: Next.js app router with server components for data fetching and client components for interactive filters.

This architecture trades strict microservices for a **single, well-structured service** that is easier to operate with a small engineering team.

## Key Technical Decisions

1. **Server Components for Data Fetching**
   - Use server components for all dashboard shells to keep data fetching close to the backend.
   - Result: fewer client-side data-fetching hooks and a smaller JS bundle.

2. **Pre-computed Aggregations**
   - Introduced nightly jobs to pre-compute the heaviest aggregations (e.g., weekly cohort churn).
   - Result: reduced dashboard load time from ~2.5s to under 600ms for key views.

3. **Typed API Contracts**
   - Shared TypeScript types between route handlers and frontend components.
   - Result: removed an entire class of “shape mismatch” bugs and made refactors safe.

4. **Role-based Access Control**
   - Implemented RBAC where support, product, and engineering see tailored subsets of dashboards.
   - Result: reduced cognitive load and simplified permissions checks in the UI.

## Challenges

1. **Query Performance**
   - Early versions used naive `GROUP BY` queries on large tables.
   - Fixed by adding compound indexes, limiting time ranges by default, and introducing pre-computed aggregates.

2. **Data Consistency Across Sources**
   - Different tools used different identifiers for the same user.
   - Solved with a dedicated identity mapping table and a normalization layer in the ingestion pipeline.

3. **Keeping the UI Fast Under Heavy Filters**
   - We moved expensive client-side computations (like large dataset sorting) to the server and returned ready-to-render data.

## Improvements

- Add anomaly detection for key metrics to proactively flag regressions.
- Introduce a configuration UI so non-engineers can define new dashboards using existing metrics.
- Replace cron-based ingestion with event-driven ingestion for lower latency.
